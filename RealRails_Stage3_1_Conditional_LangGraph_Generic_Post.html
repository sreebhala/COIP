Post Objective

Stage 3.1 is a controlled architectural upgrade after Stage 3. The goal is to move from a linear LangGraph flow into a conditional graph flow where different cases can take different agent paths.

Current Repomix→Product Feeders→AI Finds Route Opportunities→LangGraph Routing→Frontend Flow Demo
Important: Do not add LLM in Stage 3.1. Do not rewrite the product. Do not break the Stage 3 graph endpoint or the legacy deterministic endpoint.

AI Should First Discover Conditional Routing Opportunities

AI should not blindly add routes. It should inspect the project and identify where conditional routing naturally fits.

Case Type Changes

Does a normal case require fewer agents than a high-risk case?

Risk-Based Branching

Should high-risk cases go through additional review agents?

SLA / Urgency

Should delayed or urgent cases route to escalation or SLA review?

Missing Data

Should incomplete cases stop normal execution and go to data quality/manual review?

Compliance / Governance

Do some cases require policy, compliance, audit or approval routing?

Human Review Boundary

When should the graph recommend human review instead of continuing automated flow?

Expected discovery output: AI should propose 3–5 project-specific conditional routes and explain why each route is valid.

Implementation Expectations

Stage 3.1 should create a route-aware backend and a route-visible frontend.

Backend

LangGraph Changes

  • Extend WorkflowState with routing fields.
  • Add route discovery / route decision functions.
  • Add conditional edges using LangGraph.
  • Preserve deterministic agent logic.
  • Expose selected route, route reason, executed path and skipped agents.
  • Record route decision in audit trail.
Frontend

Demo Flow Changes

  • Add scenario selector for multiple case types.
  • Show selected route and route explanation.
  • Show graph execution path visually.
  • Separate executed agents from skipped agents.
  • Show final recommendation and audit reference.
  • Make the route change easy to explain in demo.

Your task has 4 parts.

PART 1 — Discover Conditional Routing Opportunities
Inspect the Product Bible, domain guide, agent architecture and Repomix.
Identify where conditional routing naturally fits this project.
Do not invent artificial routes.
Find real workflow conditions such as:
- case type
- risk level
- missing data
- SLA/urgency
- compliance requirement

- human review requirement
- escalation requirement

For each proposed route, explain:
- route name
- triggering condition
- agents to execute
- agents to skip
- business reason
- frontend demo scenario

PART 2 — Backend LangGraph Design
Evolve the current LangGraph implementation into conditional routing.
Requirements:
1. Preserve existing deterministic business rules.
2. Preserve legacy endpoint for regression comparison.
3. Keep current LangGraph endpoint working or add a new conditional endpoint if safer.
4. Extend WorkflowState with route_flags, route_decisions, selected_route, route_reason, executed_path and skipped_agents.
5. Add deterministic router functions.
6. Add LangGraph conditional edges.
7. Add only necessary optional nodes or agent wrappers.
8. Expose route details in API response.
9. Record route decision in audit.
10. Add tests for at least 4 project-specific scenarios.

Modify the frontend to clearly show conditional graph execution.

Rules:
- Do not introduce LLM.
- Do not rewrite unrelated code.
- Do not remove existing screens.
- Do not break existing APIs.
- Do not fake outputs.
- Use project-specific agent names and domain terms.
- Keep implementation deterministic and explainable.
- If a route is not justified by the product workflow, do not add it.

Acceptance rule:
Stage 3.1 is complete only when the frontend can demonstrate at least 4 scenarios where the selected route, route reason, executed path and skipped agents are visible and auditable.
